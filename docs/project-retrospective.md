# 单 GPU Serving Lab 项目复盘

记录日期：2026-10-24。本轮基础学习与工程范围收尾，不增加组件或实验。

## 项目定位与成果

这是一个具备可观测性、基础鉴权、过载保护和客户端失败处理策略的单 GPU LLM Serving Lab。
目标是能部署、观察并解释推理服务的行为；现有仓库与验证记录是工程证据。
它不是生产就绪平台，也没有证明学习者能独立重建全部实现。

| 相比单独启动推理容器，补充了什么 | 当前产物与证据 |
| --- | --- |
| 可复现部署 | 固定 SGLang 镜像摘要、Compose、环境变量示例、模型缓存；新部署推理通过 |
| 基础鉴权 | SGLang 静态共享 API key；缺失/错误密钥被拒绝，正确密钥可推理 |
| 可观测性 | Prometheus 与版本控制的 Grafana provisioning、12 个面板；目标与数据已确认 |
| 基础过载保护 | 最多 8 个运行请求、16 个等待请求；一次 32 请求检查中 24 个成功、8 个队列满返回 503，之后正常推理恢复 |
| 客户端失败处理 | 非流式共享总预算、有限重试、退避和抖动；六项本地模拟和一次真实请求通过 |
| 可核对的历史证据 | 六份历史压测日志、来源哈希、实验局限、分阶段验证记录 |

## 本轮理解的关键取舍

- 吞吐量提升不代表单个请求更快，需要结合 TTFT、TPOT 与排队指标判断。
- 有界队列吸收短时突发；持续过载需要拒绝，避免等待和客户端重试不断放大负载。
- 请求数不等于资源成本。输入/输出长度不同，KV cache 等资源需求也不同；并发上限不能保证不会 OOM。
- 共享 API key 只回答是否持有密钥，不提供用户身份、权限或配额。
- 客户端所有尝试与退避共享一个总预算；请求结果不确定时，自动重放可能重复消耗 GPU。
- 进程重启、服务就绪、业务请求恢复是不同问题；健康检查与重启策略也各有边界。

学习者在对话中已指出可观测性、鉴权、队列积压和请求重量的影响。
客户端等部分产物由助手实现并讲解，尚未独立动手验证学习掌握，不据此宣称全部能力已熟练掌握。

## 已知局限

- 单机、单 GPU，存在单点故障；没有高可用、按用户限流、完整权限系统、TLS 网关或告警流程。
- 8/16/5 秒是初始保护设置，没有建立真实业务负载下的容量、SLO 或 SLA。
- 排队超时已配置并确认容器加载，但未测试实际超时触发；过载检查发生在补齐超时之前。
- 自动重启与健康检查已配置，但崩溃/卡死恢复未实测。不能把配置存在写成自动恢复已验证。
- 客户端停止等待不保证服务端已取消工作；不提供 exactly-once 或流式断点恢复。
- 历史压测缺少完整环境信息；未重跑，不证明缓存或 CUDA Graph 的严格因果收益。

## 收尾状态与后续选择

本轮不追加测试或故障注入。后续只有在用户选择明确业务场景和目标后，才决定补哪些能力。
性能深入研究、网关、多 GPU、Kubernetes 等仍为可选支线，不是当前收尾的前置条件。
文档是否已提交推送，以 [学习计划](learning-plan.md) 和 Git 状态为准。
